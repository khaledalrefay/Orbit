# MVVM والطبقات المتناسبة

اقرأ عند تخطيط ميزة، أو توزيع مسؤوليات، أو مراجعة تسرب منطق البيانات إلى UI.
لا تستخدمه لتفرض إعادة تنظيم على إصلاح صغير واضح.

## مسؤوليات الطبقات

| المسؤولية | مكانها المعتاد | ما يحتاجه صاحبها |
|---|---|---|
| بناء Widget وقيود Layout وترتيب focus | View/Presentation UI | state ومعلومات مساحة العرض |
| TextEditingController وAnimationController | Stateful UI ضمن عمر المكوّن | إنشاء/dispose وربط أحداث عند الحاجة |
| تنسيق تحميل الميزة وحالاتها وأوامرها | Cubit/Bloc في Presentation | عقود بيانات وعمليات واضحة |
| اختيار مصادر البيانات وcache وفق سياسة معتمدة | Repository | مصادر Remote/Local واعتماديات محقونة |
| Dio وURL وJSON وDTO parsing | Data | إعداد transport وعقد API |
| قاعدة أعمال مستقلة أو مشتركة ذات قيمة | Domain/Use Case عند الحاجة | مدخلات وعقود مجردة دون Widgets |
| تركيب الاعتماديات والRouter | composition root | المصانع والأعمار والخيارات المعتمدة |

من الطبيعي أن يحتوي View على منطق عرض: اختيار Row/Column، labels، وحالة تركيز مؤقتة.
لا ينفذ `build` طلب بيانات أو navigation أو parsing؛ يمكن أن يعاد استدعاؤه لأسباب عديدة.
لا تنشئ ViewModel إضافيًا يحتفظ بنسخة من نفس state التي يملكها Cubit.
إذا وُجد منسق مستقل، يجب أن يكون له غرض مختلف وحدود وعمر محددان.

## اتجاه الاعتماديات

في بنية مبسطة، تعتمد Presentation على عقد Repository واضح من الوحدة القائمة.
يجوز أن يوجد العقد داخل data أو ملف contracts في ميزة صغيرة؛ لا تنشئ Domain فارغة لمجرد مكان العقد.

في Domain صريحة:
- Presentation تعتمد على Domain contracts أو Use Cases.
- Data تنفذ تلك العقود وتحوّل DTO إلى Domain models.
- Domain تبقى Dart مستقلًا عن Flutter/Dio وواجهة transport.
- composition root يعرف التنفيذ ويركّبه؛ Domain لا يعرفه.

كلا البديلين صحيح في نطاقه. لا تسمّ بنية بسيطة «خرقًا» لمجرد عدم وجود Domain.
ولا تسمّ Domain مستقلة إذا كانت نماذجها تستورد Dio أو BuildContext.

## اختيار مقدار الفصل

| الحالة | توصية | سبب وحدود |
|---|---|---|
| تحميل قائمة من مصدر واحد مع منطق بسيط | View + Cubit + Repository/Data | أقل طبقات تحقق فصلًا واضحًا |
| قاعدة مشتركة بين عدة features أو clients | عقد/منطق مستقل قابل لإعادة الاستخدام | يحتاج تحققًا من وجود مشاركة فعلية |
| عملية تجمع عدة repositories وتحمل سياسة أعمال | Use Case ذو سلوك | لا يكون مجرد forwarding تلقائي |
| شاشة عرض محلية بلا بيانات مشتركة | UI محلية وقد يكفي setState | Cubit ليس شرطًا لكل Widget |
| مشروع قائم له Domain معتمدة | اتبع قراره | لا تهدم حدوده لتوافق قالبًا عامًا |
| مشروع قائم يستخدم Bloc | حافظ على التدفق ما لم تُعتمد هجرة | Cubit default لا يساوي migration mandate |

اسأل عن Layer إضافية: ما التغيير أو الاختبار أو التكرار الذي تصبح معالجته أوضح؟
إذا كانت الإجابة مجرد «أفضل ممارسات»، فالفصل لم يُبرر بعد.

## مثال تنظيم ميزة

**[إضافة]** نموذج إرشادي لميزة catalog؛ أسماء الملفات غير إلزامية:

```text
lib/
  app/
    router.dart
    dependencies.dart
  features/
    catalog/
      presentation/
        cubit/catalog_cubit.dart
        cubit/catalog_state.dart
        views/catalog_page.dart
        widgets/catalog_list.dart
      data/
        catalog_repository.dart
        catalog_remote_source.dart
        models/item_dto.dart
```

يبدأ بـPresentation/Data. إذا أضيفت Domain فعلية، يوضع عقد repository والنموذج وقاعدة الاستخدام
فيها، وتنقل Data التحويل والتنفيذ دون نشر تفاصيل transport إلى Presentation.
`app` هنا اقتراح تركيب؛ اتبع بنية المستودع إن كانت مختلفة.
لا تنقل Widgets إلى shared إلا عندما توجد مشاركة مستقرة، ولا تكرر مجلد core دون حاجة.

مثال تدفق متكامل:
1. تضغط View «إعادة المحاولة» فتستدعي `cubit.load()`.
2. يقرر Cubit حالة loading وسياسة التكرار، ثم يستدعي Repository.
3. Repository يجلب ويحّول البيانات أو يعيد فشلًا بحسب العقد.
4. Cubit يصدر snapshot كاملة؛ View ترسمها.
5. تغير عرض النافذة يغير Layout فقط؛ لا يعيد إنشاء Cubit أو تحميل البيانات تلقائيًا.

## حدود الحالة المتجاوبة

Cubit لا يحتاج معرفة أن العرض 820px كي يحمل البيانات.
إذا غيّر breakpoint ترتيبًا فقط، أبقِ الحالة فوق الفرع المتغير.
إذا غيّر تجربة المنتج فعلًا، مثل selection تُشارك بين list/detail، حدد مالكها وعمرها.
لا تنقل كل قياسات الشاشة إلى Cubit؛ اقرأ القيود محليًا في View.

التفاصيل في [ملكية الحالة](../state/ownership-and-cubit-bloc.md)
و[التكيّف وحفظ الحالة](../ui/breakpoints-and-adaptive-layouts.md).

## التشخيص

| العَرَض | السبب المحتمل والدليل المطلوب | التصحيح والتحقق |
|---|---|---|
| request جديد عند كل rebuild | استدعاء load داخل build أو إنشاء owner هناك | نقل trigger إلى إنشاء owner/حدث معلوم، وعد الطلبات بعد resize |
| Widgets تفهم statusCode وJSON | transport تسرب عبر contract | mapping عند Data، واختبار parsing وفشل آمن |
| Cubit يستقبل BuildContext | خلط تنسيق البيانات والتنقل أو موارد View | أمر/state مستقل وeffect owner في UI |
| ViewModel وCubit يعكسان الحالة نفسها | مالكان متنافسان لذات الحقيقة | مالك واحد وعقد واضح؛ اختبر اتساق التحديث |
| Use Cases بلا منطق إلا forward | طبقات لا تضيف مسؤولية | تبسيط مع توثيق البديل عند تغيير معتمد |
| ملف feature كبير | سبب غير كاف لتقسيم حالة مستقلة | افصل مسؤولية مستقرة؛ احتفظ بالتنسيق المشترك |

لا تصلح عرضًا بمجرد إضافة folders. ابدأ بسلسلة الاستدعاء ومكان الحقيقة.

## معايير قبول

- يمكن شرح كل مسؤولية ومن يملكها دون الاعتماد على اسم المجلد.
- لا View تنفذ transport ولا Cubit يحتفظ بموارد UI دون مبرر واضح.
- كل طبقة إضافية تحمل قيمة يمكن وصفها واختبارها.
- نطاق الحالة يناسب route والميزة والتكيّف، وليس عدد Widgets.
- قرارات المشروع والتفضيلات معروفة؛ المجهول لا يتحول إلى افتراض مؤكد.
- التحقق يقيس السلوك الذي قد يكسر الفصل، مثل إعادة تحميل عند resize أو parsing غير صالح.

## حالة التحقق

توزيع المسؤوليات قورن بـ[دليل Flutter](https://docs.flutter.dev/app-architecture/guide) بتاريخ 2026-10-01.
الدليل سند للمبادئ، وليس سببًا لفرض مكتبات أو ViewModel أخرى.
التنظيم أعلاه إضافة تفسيرية ولم يُبنَ كمشروع مستقل.
